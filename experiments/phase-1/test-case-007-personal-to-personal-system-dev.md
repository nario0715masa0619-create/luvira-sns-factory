## Test Case ID
TC-007-personal-to-personal-system-dev

## Product / Service
AI活用型短納期システム開発

## Source Account Type
personal

## Target Account Type
personal

## Desired CTA Style
reply / discussion / experience_sharing

## Allowed Persona Expression
僕 / 私 / 自分 / 主語省略

## Risk Tolerance
balanced

## 元サンプル投稿（架空の personal アカウント風）

AIでコードが早く書けるようになったのはいいけど、
「とりあえず作ってみよう」が蔓延すると、後から大変なことになりそう。

MVPと本開発の区別が曖昧なまま進むと、
いつの間にかスコープが膨らんで、納期だけが先走る感じ。

個人的には、AIを使う前に「どこまで作るか」の線引きを
もっと真面目にやった方がいいんじゃないかと思う。

みんなはAI活用の開発、どうやってスコープを区切ってる？
リプで教えて。

#システム開発 #AI活用

## 元投稿の構造
- 個人の気づき/違和感: AIでコードが早く書けるのはいいが…
- 実務あるある: 「とりあえず作ってみよう」が蔓延する
- 仮説: MVPと本開発の区別が曖昧だと納期だけが先走る
- 本音: AIを使う前に「どこまで作るか」の線引きを真面目にやった方がいい
- 読者への問いかけ: みんなはどうやってスコープを区切ってる？
- CTA: リプで教えて

## 主要感情ドライバー
- 共感：AI開発のトラップ感
- 不安：スコープ蔓延、納期遅延
- 議論志向：他者の実践を聞きたい
- 仮説提示：個人的な見解

## same-type 変換時の構造維持
- source_account_type と account_type が同じ personal のため、個人の自然な入口・本音・問いかけ・リプCTAを維持する
- ただし、架空の本人実体験を強く断定しない
- 「僕も実際に失敗しました」「以前の案件で」などの具体実績・体験捏造に見える表現は避ける
- 一般化された観察・仮説・違和感は許容する

## 今回扱う第2商材の論点
- 要件整理
- スコープ管理
- MVPと本開発の切り分け
- AIコード生成のレビュー体制
- 人間承認ゲート
- 仕様変更の扱い
- 技術負債の抑制
- 短納期開発の品質管理
- 受託開発での認識ズレ防止
- 実装速度と安全性のバランス
- 納品後運用を見据えた設計

## 変換ルール
- source=personal / account=personal のため、個人の自然なトーンを維持
- 入口表現は「〜なんだけど」「〜かも」等の柔らかい表現
- 仮説・違和感を「〜じゃないかと思う」「〜気がする」等で提示
- CTAは reply / discussion / experience_sharing に寄せる
- 「リプで教えて」「どう思う？」「みんなはどうしてる？」等を使用
- ただし、具体実績・体験捏造に見える表現は避ける
- 「僕も半年前」「以前の案件で」等の強い個人経験は避ける

## 注意事項
- 元投稿は架空のサンプルである
- 実在の第三者投稿文は保存しない
- セキュリティ診断特有の論点（権限設計、APIキー、外部連携等）には引っ張られない
- 第2商材らしい論点で構成する
- allowed_persona_expression を守る
- balanced なトーンを維持する
