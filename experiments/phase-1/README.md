# Phase 1: 手動プロンプトチェーン検証

本ディレクトリは、Luvira SNS Factory（Team B: Kimi K2.7 Low-Cost 版）の
**Phase 1 手動検証**を実施するための場所です。

## Phase 1 の目的

Kimi K2.7 Code を中心とした低コスト SNS Factory が、
実際のバズ投稿を元に「構造抽出 → 商材置換 → 横展開 → 選抜」できるかを、
**人間が手動でプロンプトを順に実行しながら**検証します。

この段階では、まだ以下は行いません：

- コード実装
- API 連携
- n8n 等のワークフロー連携
- 自動投稿
- 実在の第三者投稿文のそのままの保存

## 実施手順

1. `manual-chain-test-template.md` をコピーし、検証ケースファイル（例: `test-case-001.md`）を作成する。
2. 元バズ投稿は**架空の「伸びた投稿風サンプル」**を使用する。実在の第三者投稿をそのまま保存しない。
3. `prompts/` 以下の 01 〜 10 を順に AI に入力し、各段階の出力を `result-template.md` に貼り付ける。
4. 各段階で人間が出力を確認し、崩れている場合は前の段階に戻って修正する。
5. `09-market-judge.md` の出力から、上位 5 本と最終おすすめ 1 本を選定する。
6. 人間が最終承認・棄却・修正を判断し、記録する。
7. 投稿はまだ行わない。Phase 1 ではあくまで手動チェーンの成立確認までとする。

## 使用する prompts（01 〜 10）

| 順番 | ファイル | 役割 |
|------|----------|------|
| 01 | `prompts/01-pattern-miner.md` | 元バズ投稿から構造・反応設計を抽出 |
| 02 | `prompts/02-emotion-mapper.md` | 感情ドライバーと読者心理の遷移を分類 |
| 03 | `prompts/03-skeleton-builder.md` | クライアントに置換可能な投稿骨格を作成 |
| 04 | `prompts/04-adaptation-writer.md` | 骨格をクライアント商材・ターゲットに置換 |
| 05 | `prompts/05-variation-generator.md` | 同じ骨格から 20〜50 案を生成 |
| 06 | `prompts/06-hook-specialist.md` | 各案の冒頭 1 行を強化 |
| 07 | `prompts/07-similarity-guard.md` | 元バズ投稿との類似度をチェック |
| 08 | `prompts/08-risk-filter.md` | 炎上・誇大広告・事実誤認・法務リスクをチェック |
| 09 | `prompts/09-market-judge.md` | 上位 5 本と最終おすすめ 1 本を選定 |
| 10 | `prompts/10-final-packager.md` | 人間承認用の提案書形式に整える |

各プロンプトの入出力形式については、該当ファイルを直接参照してください。

## 人間が記録すべき内容

`result-template.md` に以下を記録してください。

- test case ID
- 実行日
- 使用モデル
- prompts/01 〜 10 それぞれの出力（または出力ファイルへのリンク）
- 最終候補 5 本
- 最終おすすめ 1 本
- 人間評価コメント
- 元投稿との類似チェック結果
- 誇大表現チェック結果
- 炎上リスクチェック結果
- 事実誤認チェック結果
- 投稿可否
- 修正メモ
- 次回改善点

## 合格条件

以下すべてを満たすこと。

- [ ] 元投稿の文言コピーではなく、**構造転用**になっている。
- [ ] 商材への接続が自然である。
- [ ] 上位 5 本が人間確認に耐える品質である。
- [ ] 最終おすすめ 1 本が、実際の投稿候補として成立している。
- [ ] リスクコメントが具体的である。
- [ ] 10 段階の手動チェーンが破綻せず、最後まで実行できている。
- [ ] 実在の第三者投稿をそのまま保存していない。
- [ ] 顧客情報・機密情報を含めていない。

## 不合格条件

以下のいずれかに該当する場合は不合格とする。

- 元投稿に似すぎている（パクリ感が強い）。
- AI 臭い・機械的な表現が目立つ。
- 商材接続が不自然または無理やり。
- 誇大広告・事実誤認が含まれている。
- 10 段階の途中で出力形式が崩れている。
- 人間が確認しにくい形式で出力されている。
- クライアントの NG 表現に反している。

## commit 前レビュー手順

Phase 1 関連ファイルを commit する前に、以下を確認してください。

1. `git status` で想定外のファイル変更がないことを確認する。
2. `test-case-XXX.md` に実在の第三者投稿文が含まれていないことを確認する。
3. 機密情報（顧客名、API キー、内部データ等）が含まれていないことを確認する。
4. 新規ファイルが `experiments/phase-1/` 以下に配置されていることを確認する。
5. 既存の `docs/`、`prompts/`、`examples/` に不要な変更がないことを確認する。
6. レビュー担当者に差分を見てもらい、問題なければ commit する。

## 注意

- 本 Phase では自動化を行わず、**人間が手動でプロンプトを順番に実行**します。
- 各段階の出力は、次の段階の入力としてそのまま使える形式で保存してください。
- 生成された投稿案は、人間が最終承認するまで投稿しません。
