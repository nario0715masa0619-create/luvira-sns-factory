# Prompt Design

## 各 prompt ファイルの目的

`prompts/` 配下の 10 ファイルは、Team B の各 AI 役割に貼り付けて使う単独プロンプトである。

| ファイル | 役割 | 目的 |
|----------|------|------|
| `01-pattern-miner.md` | Pattern Miner | 元バズ投稿から構造を抽出 |
| `02-emotion-mapper.md` | Emotion Mapper | 感情ドライバーで分類 |
| `03-skeleton-builder.md` | Skeleton Builder | 投稿骨格を作成 |
| `04-adaptation-writer.md` | Adaptation Writer | 骨格をクライアント情報に置換 |
| `05-variation-generator.md` | Variation Generator | 20〜50 案生成 |
| `06-hook-specialist.md` | Hook Specialist | 冒頭フック強化 |
| `07-similarity-guard.md` | Similarity Guard | 元投稿との類似チェック |
| `08-risk-filter.md` | Risk Filter | 炎上・法務リスクチェック |
| `09-market-judge.md` | Market Judge | 上位 5 本 + 最終 1 本選定 |
| `10-final-packager.md` | Final Packager | 人間承認用資料作成 |

## Prompt 間の受け渡し

各プロンプトは以下の共通セクションを持つ。

- **Role**: この AI の役割
- **Objective**: このステップで達成すること
- **Inputs**: 前ステップから受け取る情報
- **Process**: 実行手順
- **Output Format**: 出力形式
- **Do Not**: 禁止事項
- **Quality Criteria**: 品質基準

受け渡しはテキストベースで行う。初期 MVP ではコピー＆ペーストで十分。

## account_type を共通必須入力として扱う

すべてのプロンプトは、必要に応じて `account_type`（`personal` / `corporate`）を入力として受け取る。

- `account_type` は Step 0 で確定し、以降の各ステップで引き継ぐ。
- `personal` と `corporate` では、以下の評価軸が変わる。
  - 模倣元アカウントの選定基準
  - 許容される一人称表現
  - 推奨 CTA スタイル
  - フックの尖らせ方
  - リスク許容度
  - 最終選抜基準
- `account_type` 未指定の場合は、どのプロンプトも生成・判定を進めず、人間に確認を求める。
- 特に `05-variation-generator.md`（バリエーション生成）と `07-similarity-guard.md`（類似性チェック）でも、`account_type` / `source_account_type` を保持し、個人/法人の文体・CTA・類似基準を反映させる。
- K2.7 固定運用でも、`account_type` は毎ステップ明示的に入力し、出力にも反映させる。
- `source_account_type` ≠ `account_type` の場合、単なる文体変換では不十分である。以下を変換先 `account_type` に合わせて変換する:
  - 反応設計（共感・議論・UGC か、保存・信頼・問い合わせ導線か）
  - CTA スタイル（リプ募集か、資料請求・無料相談・チェックリストか）
  - フックの方向性（本音・失敗談か、実務課題・チェック項目か）
  - リスク許容度（個人の熱量を法人の保存性・説明責任へ変換する）
  - 特に personal → corporate の場合、感情の熱量を単に安全化するのではなく、権限・API キー・外部連携・Tool 権限・Connector・未使用アカウント・説明責任など、具体的な実務論点へ変換する。
  - 特に corporate → personal の場合、法人の保存性・チェックリスト性・資料請求導線を、個人の問いかけ・仮説・議論誘発・リプCTAに変換する。ただし、架空実体験・確認不能な伝聞・実績匂わせは作らず、商材接続は軽く自然に残す。

### corporate + conservative 時の生成前制約

- `account_type=corporate` かつ `risk_tolerance=conservative` の場合、生成前に以下を強制する。
  - 根拠確認が必要な調査風・実績風表現（「当社の調査では」「導入実績では」「多くの企業で」等）を生成段階で除外する。
  - 効果保証に見える表現（「防げます」「漏洩しません」「安心です」「解決します」等）を除外する。
  - 元投稿の定型フレーズ（「小さな〇〇が大きな〇〇に」系の抽象締め等）を流用しない。
  - 商材接続は効果ではなく、成果物・確認項目・レポート・改善材料ベースで行う。
  - バリエーション生成は 20 案一括ではなく、10 案×2 バッチを標準とし、品質とリスクを両立する。

## K2.7 固定運用での注意点

1. **指示は具体的に**
   K2.7 は低コストだが、曖昧な指示には曖昧な出力になりやすい。役割・目的・形式を明確にする。

2. **段階的に実行**
   10 役割を一度に任せると情報が混線する。必ず 1 役割ずつ実行する。

3. **サンプルを含める**
   Output Format に具体例を含めると、K2.7 は形式を守りやすくなる。

4. **Do Not を強調**
   禁止事項を箇条書きで明記し、最後に再確認させる。

5. **日本語と英語の使い分け**
   日本語のSNS投稿生成では、プロンプトも日本語で統一する。

6. **コスト意識**
   1 回の推論で済む範囲に収める。必要に応じて入力を圧縮する。
   20〜50 案を一度に生成するとコスト・品質が不安定になりやすいため、必要に応じて 10 案単位などにバッチ分割してもよい。

7. **再現性の確保**
   同じ入力に対して同じ構造が出やすいよう、テンプレート化する。

## 将来、Qwen / GLM / K3 を追加する場合の拡張案

1. **プロンプトを役割ごとに分割**
   モデルごとに得意な役割を割り当てられるように、各プロンプトを独立させておく。

2. **入出力を JSON 化**
   モデル切り替えを容易にするため、中間入出力を構造化データにする。

3. **A/B テスト用の wrapper**
   同じ入力を複数モデルに渡し、出力を比較する仕組みを後から追加する。

4. **コスト・品質ログ**
   モデルごとにトークン数・実行時間・人間評価を記録するスキーマを用意する。

5. **フォールバック設計**
   K2.7 で品質課題が出た場合に K3 や Qwen に切り替える条件を事前に定義する。

## プロンプト運用の基本ルール

- 各プロンプトは単独で完結していること。
- 前ステップの出力をそのまま貼り付けられること。
- 出力は次のステップが解析しやすい構造であること。
- 必ず「Do Not」セクションを含めること。
- 品質基準は数値やチェックリストで明示すること。
